## Игорю: что проверить сейчас

1. Прочитай первые два раздела. Сверь исследовательский вопрос с тем, что ты реализуешь: отдельно рассматриваются публичный вызов Фиата — Шамира и секретные потоки при генерации ключей и подписании. Правки текста удобно оставлять прямо на строках Markdown в PR.
2. Запусти из корня проекта `python3 paper/transcript/check.py`. Достаточно Python 3 со стандартной библиотекой. Ожидаемая строка: `PASS: 201 transcript bytes; challenge 90e2cee6c6c0cb0ebf82682562d6d7d8`. Это контрольный пример исходного SQIsign 3.0. Он помогает проверить порядок полей до отладки усечения Стрибога.
3. При проверке обработчика challenge подай публичные поля из JSON непосредственно на вход обработчику. В baseline результат должен совпасть с указанным выше. Для экспериментального профиля сначала согласуем точные префиксы и усечение, затем зафиксируем отдельный ожидаемый дайджест. Повторная генерация подписи изменённой схемой может дать другое обязательство.

## Происхождение байтов

Проверяем запись `count = 0` из upstream [nist-v3](https://github.com/SQISign/the-sqisign/tree/6d017708db403bf83977fa70770fc4f7f9e9ff21), набор p324_3. Порядок полей исходного транскрипта задан алгоритмом 3.3 [спецификации](https://sqisign.org/spec/sqisign-20260901.pdf).

| Смещение, байты (начало включено, конец исключён) | Поле | Источник |
|---|---|---|
| [0, 3) | ASCII SQI | Домен исходного challenge |
| [3, 86) | Открытый ключ с hint | pk официальной записи |
| [86, 168) | Кодировка коэффициента A кривой обязательства | Восстановлена эталонным верификатором |
| [168, 201) | Сообщение | msg официальной записи |

Эталон для сравнения взят из байтов [182, 198) подписи. Файл KAT хранит подпись в первых 200 байтах sm. Коэффициент вспомогательной кривой в начале подписи отличается по назначению от коэффициента кривой обязательства, который нужен при хешировании.

Для повторного извлечения A на Linux/WSL нужны Git, Python 3, CMake и C-компилятор. Запусти `python3 paper/transcript/capture.py` и сравни строку COMMITMENT_A с commitment_A_hex в JSON. Скрипт собирает временную копию зафиксированного upstream с отключённым подписанием, выводит публичную кодировку A в точке хеширования и запускает проверку официальной подписи. Сборка и восстановление кривой опираются на upstream. Независимо проверены сборка транскрипта из полей, SHAKE256 в Python и совпадение с challenge из подписи. Объём проверки — одна официальная запись.

## Как читать перекрёстные тесты

Строка задаёт профиль подписанта, столбец — проверяющего. Здесь прогноз при сохранённых параметрах и форматах. «−» означает ожидаемое отклонение подписи при разных правилах challenge.

| Подписант / проверяющий | Исходный | Только хеш | Только ГПСЧ | Обе замены |
|---|---|---|---|---|
| Исходный | + | − | + | − |
| Только хеш | − | + | − | + |
| Только ГПСЧ | + | − | + | − |
| Обе замены | − | + | − | + |

Проверяющий пересчитывает публичный вызов. По принятой подписи он не устанавливает, какой генератор использовал подписант. После выбора версии для измерений свяжем эту таблицу с фактическими результатами на соответствующем коммите.

## Место работы среди аналогов

[Киктенко и соавторы](https://arxiv.org/abs/1904.06525) исследовали Стрибог в SPHINCS+ и сравнили с вариантом на SHA-256. [K-XMSS и K-SPHINCS+](https://doi.org/10.3390/s23177558) показывают применение корейских примитивов в хешевых схемах подписи. В нашей постановке интерес представляют две роли SHAKE256 внутри изогенной схемы, их разные последствия для совместимости и стоимость каждой замены. Формулу экспериментального ГПСЧ и метод измерений авторы сверят с финальной реализацией.
